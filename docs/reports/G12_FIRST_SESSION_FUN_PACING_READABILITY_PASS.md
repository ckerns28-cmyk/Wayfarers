# G-12 First-Session Fun, Pacing, and Readability Pass

Status: IN_PROGRESS until the G-12 runtime screenshot manifest, validators, and Agent Council report are regenerated on this branch.

Final intended authority verdict: `COUNCIL_PASS_READY_FOR_PR` once the proof below is present and passing.

## Purpose

G-12 exists because earlier passes could pass validators while screenshots still exposed major player-facing failures: patchy town composition, confusing building order, prompts fighting dialogue, ambient bark clutter, and visual proof that did not match written optimism.

This pass treats screenshots as production evidence. If the runtime proof contradicts a PASS claim, the council must fail the phase and require a same-branch code fix.

## Game Studio Playtest Method

Game Studio playtest method: boot the player-facing state, exercise representative verbs, capture screenshots, and inspect HUD/playfield obstruction before accepting written PASS claims.

The G-12 QA method follows the Game Studio playtest standard:

- boot the game into the first actionable Newport state
- exercise representative First Light verbs and quest events
- capture recurring screenshots from player-facing states
- inspect HUD/dialogue/prompt obstruction separately from world rendering
- confirm route readability from harbor to counting house to Tavern/Inn
- reject written PASS claims when screenshots show visible contradictions

## First-Session Bar

The G-12 manifest must prove:

- within 10 seconds, the first goal points toward the Counting House
- within 60 seconds, the harbor, counting-house route, Tavern/Inn, commercial avenue, and wharf work area are readable
- within 3 minutes, the player can advance the opening objective
- within 10 minutes, the player has heard a rumor and met useful NPC roles
- within 15-20 minutes, the player can reach a reward/contact/mystery hook

## Readability Fixes

G-12 adds runtime contracts so focused play states can suppress visual clutter:

- player prompts can be suppressed during scripted dialogue captures
- ambient town barks can be disabled when a prompt or dialogue panel is active
- the capture manifest records prompt/dialogue/bark overlap per screenshot
- camera focus safety checks required buildings, NPCs, and player-facing targets

The phrase `prompt/dialogue/bark overlap` is a hard QA concern for this phase. Dialogue plus prompt overlap, or prompt/dialogue plus ambient bark clutter, fails the validator.
